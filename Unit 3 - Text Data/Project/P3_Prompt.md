#### How each notebook is scored

Each notebook is scored on six dimensions — **Coverage, Justification, Code quality, Interpretation, Progress report**, and a **keystone** specific to that notebook — each rated **1 to 5**. Each dimension carries a share of the notebook's points, so the six add up to that notebook's value. Only levels 5, 3, and 1 are described; **4 and 2 are the steps between** them.

| Dimension | Share | The question | 5 | 4 | 3 | 2 | 1 |
|---|---:|---|---|---|---|---|---|
| **Coverage** | 20% | Is every required element present? | all present | — | two or more missing | — | large parts absent |
| **Justification** | 20% | Explained and defended, or just executed? | every non-obvious decision reasoned | — | describes *what*, not *why* | — | none |
| **Code quality** | 15% | Runs clean, follows conventions, correct? | no errors, conventions conform, methods right | — | errors on re-run or a method misapplied | — | does not run |
| **Interpretation** | 15% | Results read for meaning, or only produced? | read, with surprises accounted for | — | little reading | — | none |
| **Progress report** | 10% | Can the team account for its own work on the spot? | whoever is asked accounts for the work and the reasoning, unprompted | — | one member accounts for it thinly; others cannot pick it up | — | no one asked can account for the work |
| **Keystone** | 20% | Did you get the point of *this* notebook? | printed with each notebook below | — | printed with each notebook below | — | printed with each notebook below |

Progress report is why every member must be able to explain every notebook. At most progress reports one member is picked **at random** to account for a specific decision; if they cannot, the question goes to a teammate. You **MUST** be able to explain how any part of your team's code works, not just the part you wrote. **Code that no one on the team can explain does not count as submitted work.**

A rating maps straight to points — no conversion table and no curve. Your six ratings become a weighted average on the 1–5 scale, and that average is read as a fraction of five against the notebook's point value:

$$
\text{notebook score}_i \;=\; P_i \times \frac{1}{5} \sum_{k=1}^{6} w_k\, r_k
\qquad\qquad
\text{score} \;=\; \sum_{i=1}^{5} \text{notebook score}_i
$$

$r_k$ is your rating on dimension $k$, $w_k$ is its share from the table above, and $P_i$ is notebook $i$'s point value from the table at the top of this prompt. Straight 5s earns all of a notebook's points, straight 4s earns 80% of them, and straight 3s earns 60%.

> **One rule worth knowing in advance.** A number that should have raised suspicion and didn't — R² ≈ 1, accuracy ≈ 100%, any metric that is too good — caps Interpretation at **2** no matter what else is present. Every warning of that kind in this prompt is there for a reason.

### Part B — LLM distillation via pseudo-labeling

The central idea here is **knowledge distillation via pseudo-labeling**: pretend you never had IMDB's `genres` column for the training set, and instead use an LLM as a *teacher* to annotate the training plots, then train a lightweight classical model as a *student* on those noisy labels. The student is cheap to run and deployable — the teacher is expensive and slow. The question is how much accuracy you lose by substituting an LLM annotator for real ground-truth labels. Use any LLM SDK you have been shown in class (Anthropic, OpenAI, Gemini, Ollama) and document your model choice and version in a markdown cell.

**Teacher annotation (pseudo-labeling):**

- Write a prompt that asks the LLM to predict whether a given Wikipedia plot belongs to your **focal genre** (binary yes/no)
    - Include the plot text and the genre name in the prompt; instruct the model to respond with only `yes` or `no` (or a structured format you can parse reliably)
    - Wikipedia plots can be long — if a plot exceeds your model's comfortable context or your budget, truncate it and document where you cut and why
- Run the teacher on the **training-set plots only** (`X_train` from Part A) — never let it see the test set. Budget-conscious students may use a faster/cheaper model for this batch; document the tradeoff
- Annotate all **5 suite genres** in the same pass if your prompt allows it (one structured call per movie, predicting all genres at once)
- Save the pseudo-labeled result as `wiki_pseudo_labeled.csv` with columns `imdb_id`, `primaryTitle`, `wiki_plot`, and one binary column per focal/suite genre (e.g. `pred_comedy`, `pred_horror`, …)

**Teacher quality assessment:**

- Compare the teacher's pseudo-labels to the true IMDB genre labels for the focal genre across the training set
- Compute precision, recall, and F1 for the teacher against ground truth
- Report: how trustworthy is the teacher? What kinds of movies does it mis-label? Show examples
- Consider that a "wrong" teacher label is not always a teacher error — IMDB's genre tags are themselves crowd-assigned and inconsistent. Show at least one example where you think the teacher is right and IMDB is wrong

**Student model training:**

- Use `wiki_pseudo_labeled.csv` as training data; the LLM's pseudo-label (`pred_<focalgenre>`) is `y` — **not** the true label
- Train at least **ONE** full representation × classifier combination (e.g. TF-IDF + Logistic Regression); use the same GridSearchCV approach as Part A
- Address imbalance in the pseudo-labels with SMOTE as before
- **Evaluate the student on the same held-out test set from Part A** (true labels) — this isolates how much accuracy is lost from noisy pseudo-labels alone, since text domain and test set are identical to Part A
- Train suite-level student models for all 5 suite genres as well
